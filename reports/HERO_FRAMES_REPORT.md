# Анимация из нового ролика — 6 октября 2026

Аудитория и цель: посетитель выбирает автомобиль и оставляет заявку.
Концепция: сохраняется утверждённый тёмный шоурум и текущая композиция сайта.
Особенность: один и тот же полный оборот автомобиля управляется прокруткой в обе стороны на телефоне и компьютере.
Направление: действующие цвета, шрифты и подписи сохранены; плеер посетителю не показывается.
Ограничения: RU/KZ/EN, настоящие HTML-заголовки и ссылки, быстрый постер, ограниченная память, статический режим без JS и при reduced-motion.

Источник: предоставленный `hero2-60fps-1080p.mp4`. Фактическое разрешение 1920×1080, 60 fps. MP4-мастер сохраняется без перекодирования видеодорожки, с явным удалением аудио. Автомобиль, свет, надписи и движение не изменяются. Небольшая нечёткость надписей присутствует в самом исходнике; новый ролик используется целиком, без обрезки хвоста.

Техника: WebP-кадры в небольших двоичных пакетах, canvas и requestAnimationFrame. Никакого autoplay и video.currentTime в браузере посетителя. В каждом пакете 8 кадров (в последнем — 4), каждый хранится как uint32 LE длины + байты WebP. Метаданные и порядок файлов находятся в `static/hero/sequence.json`. На сервере Django подставляет реальные URL с хешами collectstatic.

При открытии сразу показывается HTML-постер. Первая порция кадров предзагружается из head с низким сетевым приоритетом, без ожидания window.load, нажатия или загрузки MP4 целиком. Постер остаётся видимым даже при задержке всех пакетов. Остальные пакеты загружаются после начала прокрутки двумя параллельными запросами; при Save-Data запрашиваются только необходимые. Декодирование во время движения переносится в Web Worker; если Worker/ImageBitmap недоступны, остаётся обычное Image-декодирование. Canvas не выделяет графические ресурсы до начала движения.

В памяти хранятся максимум 18 декодированных кадров на мобильном и 26 на компьютере: примерно 24/96 МБ пикселей плюс сжатые данные. Дальние изображения освобождаются. Положение сглаживается с учётом прошедшего времени (130 мс), быстрый переход по всему обороту ограничен 1,4 секунды. При задержке декодера сохраняется ближайший готовый кадр в направлении движения, холст не очищается. Устаревшие задания декодирования не накапливаются. Высота закреплённого экрана использует svh: изменение визуальной области при скрытии адресной строки не перестраивает pin.

|---|---:|---:|---:|---:|---:|
| Телефон | 596 | 768×432 | 6 493 780 байт | 50 772 байта | 6 016 байт |
| Компьютер | 596 | 1280×720 | 13 688 314 байт | 118 398 байт | 14 422 байта |

В каждом варианте 75 пакетов. Длительность 9,933333 с; последняя исходная позиция — 9,916667 с. Беззвучный мастер: 12 942 197 байт, в браузере посетителя не скачивается. Мобильная и настольная последовательности содержат все исходные кадры без интерполяции; масштабирование только вниз. Размер PNG-зерна сокращён до WebP 5 026 байт. Зерно статическое, отдельным слоем; пиксели автомобиля в исходных кадрах не менялись.

Воспроизводимая сборка:

```sh
python tools/build_hero_frames.py --source /path/to/hero2-60fps-1080p.mp4 --ffmpeg ffmpeg
python manage.py configure_hero_video
npm ci
npm run build
python manage.py collectstatic --noinput
```

Точные выполненные команды FFmpeg, контрольные суммы, размеры и число кадров: [hero_frames_asset.json](hero_frames_asset.json) в этой папке. Те же операции в переносимой записи:

```sh
ffmpeg -hide_banner -i INPUT.mp4 -map 0:v:0 -an -f null -
ffmpeg -hide_banner -loglevel error -y -i INPUT.mp4 -map 0:v:0 -c:v copy -an -movflags +faststart static/hero/hero-60fps.mp4
ffmpeg -hide_banner -loglevel error -y -i static/hero/hero-60fps.mp4 -map 0:v:0 -an -vf "scale=1280:-2:flags=lanczos,setsar=1" -fps_mode passthrough -c:v libwebp -quality 82 -compression_level 5 -start_number 0 DESKTOP_DIR/%04d.webp
ffmpeg -hide_banner -loglevel error -y -i static/hero/hero-60fps.mp4 -map 0:v:0 -an -vf "scale=768:-2:flags=lanczos,setsar=1" -fps_mode passthrough -c:v libwebp -quality 78 -compression_level 5 -start_number 0 MOBILE_DIR/%04d.webp
```

Пакеты и постеры собирает `tools/build_hero_frames.py`. Он копирует первый и последний уже закодированные кадры, без дополнительного сжатия постера. Для воспроизведения финальных размеров используйте исходный предоставленный файл с SHA-256 `3578ea8aed0eeefd99eeed10d222f9634055ab169fc0eae7aaf76dabbc044bb9`.

Для старых ресурсов сохранены отдельные приватные архивы перед удалением. Рабочие страницы, канонические URL, исходные SEO-тексты, импорт и структура административной панели сохранены. Настройка нового мастера и постеров выполняется миграцией 0018 и командой configure_hero_video; выбранный владельцем нестандартный ролик миграция не подменяет. Для произвольной загрузки из админки сначала нужен новый комплект кадров и manifest рядом с видео, иначе применяется статический постер.

## Проверки

Полный набор Django: 104/104 в исходном проекте и 104/104 в отдельной чистой копии. Проверка миграции: 122/122 URL, включая 95 страниц HTTP 200 и 27 предусмотренных HTTP 404, без новых редиректов. HTTP-аудит проверил 133 страницы, 105 URL sitemap, 1 238 уникальных изображений и 1 382 запроса. Единственный незавершённый пункт — публичные DNS/HTTPS/www-редиректы: loopback-адрес их не доказывает.

Playwright: Chrome и WebKit на Windows, ширина 1440 и 390; пять снимков 0/25/50/75/100%, обратный проход до кадра 0, синтетический touch-scroll, изменение визуальной области без изменения ширины, отсутствие горизонтального переполнения и плеера, no-JS/reduced-motion/сбой первой загрузки. Отдельно задерживались все пакеты: постер уже показывался до получения их данных. Начальная загрузка — ровно один пакет, без MP4. Скриншоты сохранены отдельно от чистого репозитория в `output/playwright/hero-60fps/` исходного рабочего каталога.

| Движок / ширина | Перерисовки в секунду | Интервал p95 | Конец pin, scrollY |
|---|---:|---:|---:|
| Chrome / 1440 | 86,5 | 20,3 мс | 3600 px |
| Chrome / 390 | 96,67 | 14,3 мс | 3376 px |
| WebKit Windows / 1440 | 8,83 | 133 мс | 3600 px |
| WebKit Windows / 390 | 32 | 32 мс | 3376 px |

Измерение проходит весь исходный ролик за 6 секунд: это ускоренный тест, и частота headless-отрисовки не равна гарантированным 60 FPS на устройстве. Все проверенные движки достигали последнего кадра 595 и возвращались к 0. В Windows-порту WebKit настольная отрисовка заметно медленнее, поэтому одинаковую плавность на реальном Safari пока нельзя считать подтверждённой. Реальный iPhone, Android и macOS Safari недоступны. Firefox установлен, но запуск его тестового процесса на этом Windows-компьютере завершился тайм-аутом; Firefox не отмечен как проверенный.

В диапазоне 1440×900 герой приходит к последнему кадру на 3600 px прокрутки; при 390×844 — на 3376 px. Дальше начинается выход из закреплённого баннера к форме и каталогу. Для другой высоты экрана позиция вычисляется из реальной высоты pin минус высота stage.

Финальный Lighthouse: мобильный 97, LCP 2191 мс, CLS 0, TBT 162 мс; компьютер 100, LCP 591 мс, CLS 0, TBT 0. INP на реальных пользователях не измерялся. Мобильный LCP быстрее сохранённой исходной оценки 2257 мс, но балл 98–99 в финальной сборке пока не достигнут. Подробности: `PERFORMANCE_REPORT.md` чистой копии и `hero_lighthouse_summary.json`.

Compose-файлы проверены по схеме, три конфигурации Nginx — нативным nginx -t. Docker на локальном компьютере отсутствует. Для чистой GitHub-версии добавлены отдельные проверки Linux/Django и реальной сборки/запуска Docker; результат публикуется в GitHub Actions. Подключение PS.kz, публичный DNS, HTTPS, автоматическое продление сертификата и работа GTM в боевом домене требуют проверки на конечном сервере.
